# Cost-reduction research — papers and repos to mine

ForgeOS already vendors RouteLLM, GPTCache, LLMLingua, and litellm-as-dependency
(see `ROADMAP.md` §4), so this sweep skips those except where a *specific
technique inside the paper* isn't captured by having the repo cloned. Every
entry below was fetched or searched and verified to exist; none are asserted
from memory. The honest picture: most "free money" here is mechanical
(pricing-table sync, provider cache rules, tool-output truncation) rather than
exotic — which fits the house rule that the biggest wins are deterministic
code around the model call, not a smarter model call.

| Source (link) | Type | What it is | What we take | Lands in | Priority |
|---|---|---|---|---|---|
| [FrugalGPT](https://arxiv.org/abs/2305.05176) | paper | LLM cascade + prompt adaptation + LLM approximation; cheapest model first, escalate only if a scoring function rejects the answer. Reports up to 98% cost reduction at matched accuracy. | The cascade-with-reject-function pattern and its cost/accuracy tradeoff curve methodology (not the repo — there isn't a maintained one) | `router` (escalation policy calibration) | P1 |
| [Hybrid LLM](https://arxiv.org/abs/2404.14618) (ICLR 2024) | paper | A small trained router predicts whether a cheap model's answer will match a large model's quality; a single tunable threshold trades cost for quality at test time. Reports ~40% fewer large-model calls at no quality loss. | The "single dial" design — one runtime-tunable threshold instead of a fixed routing table — as an alternative calibration surface for the router | `router` | P1 |
| [AutoMix](https://arxiv.org/abs/2310.12963) ([repo](https://github.com/automix-llm/automix)) | paper+repo | Small model self-verifies its own answer (few-shot, no extra training), then a POMDP router decides whether to escalate based on confidence, not an external judge model. >50% cost reduction at matched quality. | The self-verification-before-escalate step: today `Router.escalate` only fires on a hard `MODEL failure`; this gives a soft signal to escalate *before* failure, using the worker's own confidence | `router` (escalation policy) | P1 |
| [microsoft/best-route-llm](https://github.com/microsoft/best-route-llm) ([paper](https://arxiv.org/abs/2506.22716)) | repo+paper | Routes to a model *and* a sample count (best-of-n from a cheap model can beat a single call to an expensive one). DeBERTa-v3-small difficulty router. Reports 60% cost cut at <1% quality drop. | The difficulty-router architecture and the "more cheap samples vs one expensive call" decision rule — genuinely new, not yet vendored | `router` | P0 |
| [RouteLLM](https://arxiv.org/abs/2406.18665) | paper (repo already vendored) | Trains a router on Chatbot Arena preference data via a Bradley-Terry win-rate model, then augments with GPT-4-judged synthetic labels. | Not the code (already have it) — the *calibration recipe*: how to bootstrap threshold labels without paying for a large human-preference dataset | `router` | P2 |
| [Smoothie](https://arxiv.org/abs/2412.04692) | paper | Label-free LLM routing — estimates model competence per-input using unsupervised weak-supervision-style agreement scoring, no preference-labeled training set needed. | The label-free calibration path for days-one router bootstrap, before ForgeOS has accumulated its own accept/reject history | `router` | P2 |
| [Speculative Actions](https://arxiv.org/abs/2510.04371) | paper | Draft-then-verify for *agent actions*, not tokens: a fast model predicts the next tool call, runs it speculatively in parallel with the slow primary agent, and commits only if the primary agent's actual decision matches. Reports up to 55% next-action prediction accuracy, 20% latency cut, provably lossless (never diverges from what the primary agent would have done). | The commit-only-on-match verification gate as a pattern for speculative tool-call execution ahead of the routed worker's decision | `router` / adapter executor | P1 |
| [LLMLingua-2](https://arxiv.org/abs/2403.12968) (ACL 2024 Findings) | paper+[repo](https://github.com/microsoft/LLMLingua) | Token-classification compressor trained via GPT-4 data distillation instead of LLMLingua-1's self-information/perplexity scoring; bidirectional (encoder, not causal LM), 3-6x faster to run, 1.6-2.9x faster end-to-end, 2-5x compression. | The already-flagged "worth cloning next" item — confirmed concretely: use as the reducer's compression backend instead of LLMLingua-1's causal-LM scorer, since it's a drop-in faster+better replacement | `economy/reducer` (capsule post-pass) | P0 |
| [Selective Context](https://arxiv.org/abs/2310.06201) | paper | Prunes tokens by self-information from a small causal LM (e.g. GPT-2), percentile-based cutoff (50th percentile keeps ~57% of tokens). No training, no encoder model needed. | A zero-dependency fallback compressor for when no LLMLingua-2 model is loaded — simplest possible implementation of the same idea | `economy/reducer` (fallback path) | P2 |
| [SWE-Pruner](https://arxiv.org/abs/2601.16746) | paper ([repo](https://github.com/Ayanami1314/swe-pruner)) | Coding-agent-specific context pruning: the agent states an explicit goal ("focus on error handling"), and a lightweight 0.6B "skimmer" model selects relevant lines given that goal — task-aware, not perplexity-based, so it preserves syntax/logic structure that generic compressors break. 23-54% token reduction on SWE-bench-style agent tasks, up to 14.84x on single-turn tasks. | Goal-conditioned line selection for the capsule builder — instead of (or alongside) static symbol-rank ordering, prune by "what does *this* task step actually need," which is exactly the capsule's job | `economy/capsule` | P0 |
| [vCache](https://arxiv.org/abs/2502.03771) | paper ([repo](https://github.com/vcache-project/vCache)) | Semantic cache with a *verified* error rate: learns an online, per-prompt similarity threshold instead of GPTCache's one static global threshold, so cache hits come with a formal bound instead of a guess. | The per-prompt online-threshold-learning algorithm as an upgrade to the already-planned GPTCache integration — matches ForgeOS's own "measured, not asserted" ethos better than a static-threshold cache does | `economy` (preflight refusal / semantic cache) | P1 |
| [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) | docs | Up to 4 explicit `cache_control` breakpoints per prompt; default TTL 5 min (refreshes on each hit) or opt into 1h; cache write costs 25% more than base (5 min) or 100% more (1h); cache read is 10% of base price. | The exact breakpoint-placement and TTL-refresh rules the byte-stable prefix compiler (`prompts/prefix.py`) must respect to actually earn the cache discount it's designed around | `prompts/prefix.py` | P0 |
| [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) | docs | Fully automatic — no explicit markers. Matches the longest previously-seen prefix in 128-token increments, starting at a 1024-token minimum before any caching applies at all. 50% discount, cache evicted after 5-10 min idle, always gone within 1h. | The provider-specific minimum-prefix-length constraint (1024 tokens) — the prefix compiler needs to know this floor exists per-provider, since packing a shorter prefix for OpenAI wastes the whole mechanism | `prompts/prefix.py`, `gateway` | P0 |
| [DeepSeek context caching](https://deepseek.ai/pricing) | docs/pricing page | Automatic disk-based caching since Aug 2024, no headers or SDK changes; cache hit is ~1/10 of standard input price. The widely-repeated "off-peak discount" (50-75% off) applied only to the legacy V3/R1 generation and, as of the 2026-07-21 pricing page, has **no equivalent for V4** — worth correcting since it's still cited as current in some notes. | Confirms DeepSeek needs no `cache_control`-style tagging (unlike Anthropic) — one less code path — and flags the off-peak claim as stale so it isn't relied on for scheduling | `gateway`, `quota` | P1 |
| [SGLang / RadixAttention](https://arxiv.org/abs/2312.07104) | paper | Self-hosted inference engine shares KV cache across *any* requests with a common prefix via a radix tree, giving partial credit for shared sub-prefixes rather than requiring one exact full-prefix match. | The radix-tree data structure as a design upgrade path for `prompts/prefix.py`: today's byte-identical-whole-prefix requirement could get partial hits on shared *sub*-prefixes across different task capsules. Only relevant if ForgeOS ever hosts local models directly (vLLM/SGLang), not for provider APIs. | `prompts/prefix.py` (future) | P2 |
| [Preble](https://arxiv.org/abs/2407.00023) | paper | Distributed LLM serving scheduler that routes each request to whichever replica already holds a warm matching KV cache, trading cache locality against load balance; 1.5-14.5x latency improvement over cache-blind schedulers. | The "route to the worker that already has this warm" idea — relevant once ForgeOS is scheduling across multiple local Ollama instances or long-lived CLI sessions, not just picking a price tier | `router` | P2 |
| [Anthropic Message Batches API](https://anthropic.com/news/message-batches-api) | docs | Async endpoint, up to 100k requests/batch, 50% off both input and output tokens, 24h SLA (usually much faster). | A concrete batch-lane submission format for non-interactive work (summarization, testselect scoring, reducer passes) that don't need a synchronous response | `quota`/capacity market | P1 |
| [OpenAI Batch API](https://developers.openai.com/api/docs/guides/batch) | docs | `.jsonl` submission, up to 50k requests/file, flat 50% discount both directions, `completion_window` fixed at `"24h"`. | Same batch-lane concept, OpenAI's specific submission shape — worth wiring as a second batch backend alongside Anthropic's | `quota`/capacity market | P1 |
| [Anthropic context editing (`clear_tool_uses_20250919`)](https://platform.claude.com/docs/en/build-with-claude/context-editing) | docs | Server-side, parameterized algorithm: once input tokens cross a `trigger` threshold (default 100k, configurable), clear the oldest tool_use/tool_result pairs first, keep the most recent N (`keep`, default 3), never clear below a `clear_at_least` token floor (avoids cache-thrashing from tiny clears), optionally `exclude_tools` from ever being cleared, and substitute placeholder text so the model knows something was removed. | The whole algorithm is provider-agnostic and cheap to reimplement client-side for *any* worker: threshold-triggered, oldest-first, floor-guarded tool-output clearing. This is a concrete, already-shipped reference design for exactly what the reducer needs to do for long agent sessions | `economy/reducer` | P0 |
| [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp) | engineering blog (Anthropic) | Instead of loading every tool definition and routing every intermediate tool result through the model's context, present tools as a code API and let the agent write a script that calls them directly, filters/aggregates locally, and returns only the final reduced result to the model. Anthropic's own example: 150,000 tokens down to 2,000 (a 99% cut) for a multi-tool task. | The core move — don't let raw tool output touch the model's context at all when the orchestration logic is expressible as code — is the largest single number in this whole sweep and matches ForgeOS's own "the cheapest call is the one never made" lever almost exactly | `economy/reducer`, adapter executor | P0 |
| [MCP pagination spec](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/pagination) | spec | Opaque cursor-based pagination for list operations, with an [open discussion](https://github.com/modelcontextprotocol/modelcontextprotocol/discussions/799) proposing extending the same cursor pattern to *any* tool response that can be arbitrarily large. | The cursor-continuation shape as the format for any ForgeOS-side tool wrapper (search, grep, log tail) whose output could be huge — return a page plus a cursor, let the model ask for more only if it needs to | `economy` (tool-output handling) | P1 |
| [EcoAssistant](https://arxiv.org/abs/2310.03046) ([repo](https://github.com/JieyuZ2/EcoAssistant)) | paper+repo | Agentic code-execution cascade: cheap model first, escalate on failure (assistant hierarchy — already covered by cascade routing above), *plus* "solution demonstration" — retrieve past successful query→code solutions and use them as few-shot examples for new similar queries. 30-50% additional cost cut over the hierarchy alone. | The solution-demonstration idea specifically: a semantic cache of *past successful task solutions* (not just Q&A text) reused as a prior, so ForgeOS doesn't re-derive a plan/patch shape it has already solved before | `economy` (preflight refusal) / `testselect` | P1 |
| [cheahjs/free-llm-api-resources](https://github.com/cheahjs/free-llm-api-resources) | repo (data) | Actively-maintained community list of every provider's free tier, with rate limits and quotas, kept current as providers change terms. | An external ground-truth feed to cross-check ForgeOS's own dead-model store (`gateway/dead_models.py`) instead of relying solely on self-probing — catches free-tier changes before ForgeOS's own probes would | `gateway`, `quota` | P1 |
| [BerriAI/litellm `model_prices_and_context_window.json`](https://github.com/BerriAI/litellm/blob/main/model_prices_and_context_window.json) | repo (data file) | A single JSON file, auto-synced by CI, listing per-token prices and context windows for 100+ providers and thousands of models — the de facto community-canonical pricing table, usable without depending on the litellm runtime at all. | Pull this file directly as the ledger's price table data source instead of hand-maintaining prices — directly prevents the "stale hardcoded prices" flavor of free-tier rot that's already a named failure mode | `ledger` | P0 |
| [songquanpeng/one-api](https://github.com/songquanpeng/one-api) ([new-api fork](https://github.com/QuantumNous/new-api)) | repo | Single-binary multi-provider gateway: key-pool rotation, per-channel priority groups, auto-disable on error, cross-format conversion (OpenAI/Claude/Gemini-compatible). | A second, differently-shaped reference design for channel-priority-groups-with-auto-disable to diff against ForgeOS's own `dead_models.py` (terminal vs temporary) — same problem, worth comparing approaches | `gateway` | P2 |
| [Mirrowel/LLM-API-Key-Proxy](https://github.com/Mirrowel/LLM-API-Key-Proxy) | repo | Narrower single-purpose "rotator_library": automatic key rotation, failover on error, rate-limit-aware cooldowns. | A smaller, easier-to-read reference than one-api for the exact cooldown/failover state machine (temporary-cooldown vs permanent-failover) | `gateway` | P2 |

## Top 5 actions (novelty × demand ÷ effort)

1. **Pull `litellm/model_prices_and_context_window.json` into the ledger.** Trivial effort (fetch + parse one CI-synced JSON file), directly fixes the named "stale hardcoded prices" failure mode, and needs zero dependency on the litellm runtime. Highest ratio in the set.
2. **Harden `prompts/prefix.py` with provider cache-mechanics.** Anthropic's up-to-4-breakpoints/TTL-refresh rules and OpenAI's 1024-token cache floor are cheap to encode and directly protect the flagship byte-stable-prefix tool from silently missing the cache discount it exists to earn.
3. **Port the `clear_tool_uses_20250919` algorithm into `economy/reducer`.** It's a fully-specified, already-shipped reference design (threshold trigger, keep-last-N, clear-at-least floor, exclude list) — copy the shape, make it provider-agnostic, done.
4. **Adopt the "code execution with MCP" pattern for tool-heavy jobs.** Biggest single number found (150k→2k tokens, 99%) and philosophically identical to ForgeOS's "the cheapest call is the one never made" — worth a real design pass even though the effort is a genuine architecture change (a code-exec lane in the executor), not a one-file port.
5. **Wrap GPTCache with vCache's per-prompt online threshold.** Matches ForgeOS's "measured, not asserted" identity better than any other source here — turns the semantic cache from "probably fine" into a cache with a stated, learned error bound, which is exactly the kind of receipt this project already builds everything else around.
